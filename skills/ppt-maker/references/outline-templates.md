# 문서 유형별 목차 템플릿

작성일 2026-09-08, 2026-09-18 기획서 6장 기준으로 다시 씀.
스킬이 아웃라인을 만들 때 쓰는 기본 골격이다.

## 1. PPT 를 구분하는 기준

| 기준 | 종류 | 예·조건 |
| --- | --- | --- |
| 목적 | 제안서 | 정부 과제 제안서, 고객사 제안서 |
| | 보고서 | 연차보고서, 내부 진행보고 |
| | 소개서 | 회사 소개서, IR(투자자) |
| 제출 조건 | 자유 양식 | 제한 없음 |
| | 지정 양식 | 분량 제한, 목차 제한 |
| 읽는 방식 | 발표용 | 글자·이미지 크게, 시각자료 풍부, 깔끔하게. 문체는 누구나 이해하기 쉽게 핵심만 |
| | 제출·열람용 | 텍스트 밀도 높게, 읽기 쉽게. 문체는 전문적이고 신뢰감 있게 |

텍스트가 적으면 전문적으로 보이지 않고, 많으면 잘 안 읽힌다.
텍스트를 얼마나 넣을지는 **읽는 방식**을 기준으로 정한다.

### 읽는 방식 → 밀도
| 읽는 방식 | `meta.density` | 장표당 |
| --- | --- | --- |
| 발표용 | `airy` | 메시지 하나. 수치는 크게, 불릿은 3개 이내 |
| 제출·열람용 | `dense` | 근거까지 한 장에. 표·카드로 묶어 읽는 순서를 잡는다 |

### 제출 조건
`자유 양식`이면 장수는 아래 템플릿 권장값을 따른다.
`지정 양식`이면 **분량·목차 제한을 먼저 받아 적고** 그 안에서 섹션을 줄인다.
공고문에 목차가 지정돼 있으면 템플릿보다 공고문 목차가 우선이다.

## 1-2. 공통 규칙

### 장표 문법 (모든 본문 장표)
```
아이브로우    그 장표가 속한 섹션 이름          ← 어디를 읽고 있는가
헤드라인      결론을 명사형으로                 ← 그래서 무엇인가
리드          1~2문장                          ← 전제·집계 기간·근거
본문          카드 / 표 / 도식 / 수치
```

### 고정 장표
| 위치 | 장표 | 필수 | 구성 |
| --- | --- | --- | --- |
| 1 | 표지 | 필수 | 설명줄 / 제목 / 왼쪽 아래 로고 / 오른쪽 아래 상자 |
| 2 | 목차 | 권장 | 4~7개 섹션, 번호 + 제목 |
| 섹션 시작 | 간지 | 선택 | 섹션이 3개 이상이면 자동(`meta.dividers`) |
| 끝-1 | 마무리 | 필수 | 핵심 한 문장 / 회사명 / 연락처 |
| 끝 | 부록 | 선택 | 질의 대비 상세 자료 |

### 입력 수집 (공통)
- 목적·제출 조건·읽는 방식
- 메인 컬러(필수), 보조 컬러(선택), 로고 파일
- 회사명, 발표자·작성자, 날짜
- 원문 텍스트 또는 기존 PPTX
- 유형별 추가 질문은 각 유형의 "필수 입력"

## 2. 레이아웃 매핑 (레퍼런스 템플릿 24종 기준)

템플릿의 24종 슬라이드를 이 스킬의 블록으로 옮긴 표다. 표지·목차·간지·마무리 4종은 `outline.json` 의 `meta` 만으로 자동 생성되고, 나머지 20종은 본문 장표의 `blocks` 로 만든다.

| # | 템플릿 레이아웃 | 이런 내용일 때 | 이 스킬에서 쓰는 블록 |
| --- | --- | --- | --- |
| 01 | Cover — Dark Brand | 표지 | 자동(`meta.title/subtitle/orgs/date`). 다크 표지 한 종만 쓴다 |
| 02 | Cover — Clean Light | 밝은 표지 | 쓰지 않는다(01 로 통일) |
| 03 | Agenda | 목차 | 자동(`meta.agenda`). 번호 + 섹션명만 |
| 04 | Section Divider | 단원 시작 간지 | 자동(`meta.dividers`, 목차 3개 이상이면 들어감) |
| 05 | Title + Bullet Points | 항목 3~5개 나열 | `bullets`. 4개 넘으면 `columns`/`cards` 로 |
| 06 | Title + Image Right | 텍스트 설명 + 화면·사진 | `image` (`side:"right"`, `text:{heading, items}`) |
| 07 | Title + Image Left | 이미지가 주인공, 설명은 보조 | `image` (`side:"left"`) |
| 08 | Two Columns — Equal | 두 항목을 같은 비중으로 | `columns` 2개. 전·후 대비면 `compare` |
| 09 | Three Column Cards | 환경·현황을 세 갈래로 | `cards` 3개 |
| 10 | Stats / Metrics | 성과·수치 강조 | `stats` 2~4개. 추이가 있으면 `chart`, 근거는 `table` |
| 11 | Full Bleed Image | 구성도·시연 화면 전면 | `image` (`side:"full"`) |
| 12 | Table — Comparison | 비교, 평가지표 대응, 예산 | `table` (`emphasize` 로 강조 열) |
| 13 | Quote / Testimonial | 고객 발언, 인용 | `callout` (`text`, `label:"고객 의견"` 등) |
| 14 | Timeline | 일정·연혁, 시점이 핵심 | `timeline`. 기간·동시 진행이 핵심이면 `table` 간트형 |
| 15 | Problem → Solution | 문제와 해결을 맞대어 | `compare` (`tag` AS-IS/TO-BE 또는 문제/해결) |
| 16 | Process Steps | 절차·파이프라인, 순서가 핵심 | `process` 3~5단계. 분기·반복이 있으면 `image` 흐름도 |
| 17 | 2×2 Image Grid | 시연·사례 사진 4장 | `columns` 2개(`image` 포함) 블록을 위아래 2개 |
| 18 | Team Members | 팀·조직 | `cards` 4개(`cols:4`, 제목=이름, 설명=역할). 사진은 넣지 않는다 |
| 19 | Closing / Thank You | 마무리 | 자동(`closing.message/sub`, `meta.contact`) |
| 20 | Company Overview | 회사 소개 + 지표 | `columns` 2개(좌 소개·특징, 우 `stat`) 또는 `columns` + 아래 `stats` |
| 21 | Solution Feature (A-type) | 기술 모듈 하나를 깊게 | `image` (`side:"right"`) + 아래 `callout` |
| 22 | Technical Proposal (Split) | 도전과제 ↔ 솔루션 비교 | `compare`, 표가 필요하면 `columns`(좌 items) + `table` |
| 23 | R&D Project Background | 과제 배경 + 목표 4개 + 기술 태그 | `cards` 4개(`cols:2`) + `callout`(기술 태그) |
| 24 | Client / Partner Logos | 고객·파트너 로고 | `columns` 3개(`image`) 블록 2개. 로고 파일이 없으면 자리표시자 |

블록 필드는 `outline-schema.md` 의 "블록 타입" 표를 따른다.
레이아웃 칸의 번호(`09 카드3` 등)는 이 표의 번호다.

## 4. 기존 PPTX 개선 모드에서의 목차 매핑

올린 PPTX 의 장표 제목을 읽어 위 6가지 중 가장 가까운 유형을 고르고 이 순서로 간다.
1. 고른 유형과 매핑 결과를 표로 보여 주고 확인받는다(장표 → 템플릿 카테고리).
2. 빠진 카테고리는 "추가 권장"으로, 템플릿에 없는 장표는 "유지 / 부록으로 / 삭제" 중에 고르게 한다.
3. 원문은 뜻을 그대로 두고 리드 메시지만 새로 쓴다. 수치는 바꾸지 않는다.
