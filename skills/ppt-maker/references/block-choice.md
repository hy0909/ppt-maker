# 블록 고르는 기준

장표마다 "이 내용을 어떤 모양으로 보여 줘야 한눈에 들어오나"를 정하는 규칙이다.
필드 형식은 `outline-schema.md`, 개수·글자 수 한계는 `deck-rules.md` 에 있다. 여기서는 **고르는 순서와 근거**만 다룬다.

## 1. 고르는 순서

1. **장표의 메시지 한 줄을 먼저 쓴다.** 제목(`title`)이 곧 메시지다. 블록은 그 메시지를 증명하는 그림이다.
2. **원문에서 신호를 찾는다.** 아래 2절 표의 왼쪽 열. 숫자가 있나, 시간이 흐르나, 순서가 있나, 대립이 있나.
3. **신호가 여럿이면 메시지에 가장 가까운 것 하나를 고른다.** 예: 월별 숫자가 있어도 메시지가 "세 지표 모두 목표 달성"이면 추이(chart)가 아니라 결과(stats·cards rows).
4. **신호가 없으면** 병렬 주제(columns·cards)로 간다. bullets 는 그래도 안 될 때만.
5. **`why` 에 근거를 한 줄 적는다** (5절).
6. **앞뒤 장과 겹치는지 본다** (4절). 겹치면 내용이 허락하는 다른 블록으로 바꾸거나 장을 합친다.

## 2. 신호 → 블록

| 원문의 신호 | 블록 | 알아보는 말 |
| --- | --- | --- |
| 같은 지표가 시간에 따라 변한다 (4개 시점 이상) | `chart` (line) | "월별", "분기별 추이", "1월 → 6월" |
| 항목끼리 크기를 비교한다 (같은 단위 숫자 3개 이상) | `chart` (bar) | "채널별", "지역별 매출", "A사 ○, B사 ○" |
| 숫자 2~4개가 그 자체로 결론이다 | `stats` | "누적 120만", "정확도 98%", "3개월 만에" |
| 숫자 하나 + 전기 대비 변화가 항목마다 있다 | `cards` + `rows`·`highlight` | "7월 ○ → 8월 ○, 18% 증가" |
| 순서대로 거치는 단계가 있다 (앞이 끝나야 뒤가 시작) | `process` | "먼저", "그다음", "~후", "1단계" |
| 단계마다 날짜·기간이 붙는다, 겹치지 않는다 | `timeline` | "1분기에 ○, 2분기에 ○" |
| 여러 일이 같은 기간에 동시에 돈다 | `gantt` | "3~5월 개발, 4~6월 테스트" |
| 회사가 지나온 해마다 있었던 일 | `history` | "2021년 설립, 2023년 투자 유치" |
| 사람·팀의 역할 배치 | `org` | "PM 1명, 개발팀 4명", "총괄 ○○" |
| 전 ↔ 후, 문제 ↔ 해법 두 편이 맞선다 | `compare` | "기존에는", "도입 후", "반면" |
| 여러 대상을 같은 기준 여러 개로 잰다 (가로·세로가 다 의미 있음) | `table` | "항목별 비교", "요구사항 대응", "예산" |
| 동등한 항목 2~3개, 항목마다 설명이 길다 | `columns` | "세 가지 축", "두 가지 방식" |
| 동등한 항목 3~6개, 항목마다 짧다 | `cards` | "주요 기능 4가지", "서비스 5종" |
| 구성도·화면·사진이 있어야 이해된다 | `image` | "시스템 구성", "앱 화면", "현장 사진" |
| 대등한 항목 3~4개를 그림 한 장씩으로 기억시킨다 | `figcards` (side) | "네 가지 효과", 항목마다 장면이 떠오름 |
| 상황·장면이 다른 문제 3개 (사진 + 질문 + 결론) | `figcards` (top) | "누구를, 언제 …할 것인가" |
| 장비·화면의 부위별 기능 | `annotate` | "전면에 카메라, 뒷면에 화면", 부위 이름 나열 |
| 짧은 처리 단계 3~5개, 단계마다 한두 줄 | `process` (circle) | "검출 → 판별 → 추출 → 매칭" |
| 단계마다 기간·할 일·완료 기준 | `process` (chevron) | "1단계 약 2주 … 완료 기준" |
| A 에 B 를 더하면 효과가 이렇다 | `compare` + `result` | "기존에는 … 더하면 → 효과" |
| 예상 질문과 답 | `qa` | "Q.", "…않나?", 우려 사항 |
| 가장 센 숫자 하나 + 받쳐 주는 숫자 몇 개 | `bigstat` | "유출 0%", 숫자마다 의미 한 줄 |
| 방법마다 대표 효과가 퍼센트 하나 | `cards` + `bar` | "기간 50% 단축", "비용 70% 절감" |
| 장표의 결론·주의 사항을 한 번 더 못 박는다 | `callout` (다른 블록 아래) | "요약하면", "단, ~ 주의" |

`flow`(흐름 띠)·`strip`(라벨 띠)도 주 블록이 아니다. 본문 아래에 붙여 순서·대상·지표를 한 줄로 정리할 때 쓴다(`layout-patterns.md` 4절).

`callout` 은 주 블록이 아니다. 위험·주의 사항이 여러 개면 본문은 `cards`(항목마다 무엇·영향·대응)로 그리고, `callout`(tone `warn`)은 그 아래 결론 한 줄로만 쓴다.

## 3. 헷갈리는 짝 가르기

### columns vs cards
- **항목 수**: 2~3개면 columns, 4개 이상이면 cards.
- **항목 길이**: 항목마다 소제목+불릿 여러 줄(sections)이면 columns. 이름+한두 줄이면 cards.
- **동등성**: 둘 다 "서로 대등한 것들"이다. 순서가 있으면 둘 다 아니고 process.
- 숫자 비교(전월 대비)가 들어가면 cards 의 `rows`·`highlight`.

### process vs timeline vs gantt
- 시간 표시가 **없고** 순서만 있다 → `process`.
- 단계마다 **기간이 붙고** 서로 **겹치지 않는다** → `timeline`.
- 기간이 **겹친다**, 또는 일이 4개 이상이라 막대로 봐야 한다 → `gantt`.
- 과거의 사건 목록(회사 연혁)은 셋 다 아니고 `history`.
- 시험법: "앞 단계가 끝나야 다음이 시작하나?" 예 → process/timeline, 아니오 → gantt.

### table vs chart vs stats
- 숫자가 **2~4개**이고 각각이 결론이다 → `stats`.
- 숫자가 **한 지표의 여러 시점** 또는 **같은 단위의 여러 항목**이다 → `chart`. 표로 나열하지 않는다.
- 숫자보다 **글(조건·설명)이 많거나 기준이 여러 개**다 → `table`.
- 시험법: "읽는 사람이 위아래·좌우를 둘 다 훑어야 하나?" 예 → table. "모양(오르내림·크기 차이)이 메시지인가?" 예 → chart. "숫자 몇 개만 기억하면 되나?" 예 → stats.

### compare vs table vs columns
- 딱 **두 편**이고 한쪽이 나은 쪽(TO-BE·해법)이다 → `compare`.
- 셋 이상을 비교하거나, 두 편이라도 기준이 4개 넘게 나란히 맞물린다 → `table`.
- 두 편이 대립이 아니라 그냥 다른 주제다 → `columns`.
- **"난제 → 해법"·"문제 → 대응" 쌍이 여러 개**면 쌍마다 카드를 만들지 않는다. 왼쪽 난제·오른쪽 해법으로 줄을 맞춘 `compare`(쌍 3~4개), 쌍이 5개 넘거나 기준이 더 붙으면 `table`. columns 로 쌍을 나누면 "무엇이 무엇을 푸는지" 대응이 안 보인다.

### stats vs cards(rows·highlight)
- 지표마다 숫자 **하나**만 보여 준다 → `stats`.
- 지표마다 **두 시점 값 + 변화율**이 있다 → `cards` 의 `rows` + `highlight`.

### image vs 나머지
- 원문에 그림·화면이 실제로 있거나, 말로는 구조가 안 그려질 때만 image. 이미지 파일이 없으면 자리표시자가 남으니 사용자에게 받을 것을 `[입력 필요]` 목록에 적는다.

### stats vs bigstat
- 숫자들이 **대등하다** → `stats`.
- 숫자 하나가 **압도적으로 중요하고** 나머지가 받쳐 준다 → `bigstat`. 숫자마다 "그래서 무슨 뜻인지" 한 줄이 있어야 한다.

### cards vs figcards
- **원문에 그림·사진이 첨부됐거나 사용자가 그림을 주기로 했을 때만** `figcards`. 장면이 떠오르는 말만으로는 고르지 않는다.
- 그 밖에는 `cards`. 인용·발언·개념·정책은 그림이 없으면 `cards`. 그림 자리만 비워 둔 `figcards` 는 만들지 않는다.

## 4. 다양성 규칙

비슷한 모양이 이어지면 읽는 사람이 장이 넘어간 걸 못 느낀다. 아래는 아웃라인을 다 쓴 뒤 덱 전체를 놓고 본다.

- **같은 주 블록이 3장 연속이면 안 된다.** 주 블록 = 장표의 첫 블록(callout·flow·strip 제외). 내용이 정말 같은 모양이면 장을 합치거나, 가운데 장을 다른 각도(숫자 → stats, 비교 → compare)로 다시 본다.
- **한 블록이 본문 장의 40%를 넘지 않는다.** columns·cards 쏠림을 막는다.
- **본문이 6장 이상이면 블록 종류가 최소 4가지.**
- **숫자가 있는 덱이면 stats·chart 중 하나는 들어간다.** 숫자를 글로만 나열하지 않는다.
- **bullets 는 덱 전체에서 1장 이하.**
- 바꾸려고 억지로 다른 블록을 쓰지 않는다. 신호와 안 맞는 블록은 단조로움보다 나쁘다. 그럴 땐 장 순서를 바꾸거나 장을 합친다.

`scripts/check_blocks.mjs <outline.json>` 이 위 규칙과 `why` 누락을 검사한다(빌드 전에 돌린다).

## 5. `why` 쓰는 법

장표마다 `slide.why` 에 **"신호 → 블록"** 한 줄을 쓴다. 렌더러는 읽지 않는다(장표에 안 보인다). 사용자가 아웃라인을 확인할 때 판단이 틀린 곳을 바로 짚게 하는 용도다.

- 좋은 예: `"월별 방문자 6개월 추이 → chart(line)"`, `"요구사항 분석 → 설계 → 개발 순서, 기간 없음 → process"`, `"도입 전후 두 편 대립 → compare"`
- 나쁜 예: `"보기 좋아서"`, `"내용이 많아서 columns"`, `"cards"`(근거 없음)
- 다양성 때문에 바꿨으면 그것도 적는다: `"병렬 세 가지지만 앞 두 장이 cards → columns"`

## 6. 시험 세트

`tests/block-choice/cases.json` 에 원문 조각과 정답 블록이 있다. 이 문서를 고치면 돌려서 맞히는 비율이 떨어지지 않았는지 본다.

```bash
node scripts/eval_block_choice.mjs            # claude CLI 로 사례마다 블록을 고르게 하고 정답과 비교
node scripts/eval_block_choice.mjs --only 3,7 # 특정 사례만
```

틀린 사례가 나오면 (1) 이 문서의 기준이 모호한지, (2) 정답이 틀렸는지 먼저 본다. 실제 덱에서 사람이 바로잡은 장표는 사례로 추가한다.
