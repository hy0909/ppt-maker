# 문서 유형별 목차 템플릿

스킬이 아웃라인을 생성할 때 사용하는 기본 골격. 일곱 가지 문서 유형별로 섹션 순서와 각 장표의 역할을 정의했다.

---

## 0. 공통 규칙

### 장표 문법 (모든 본문 장표)
```
헤더        N. 섹션명 – 소제목                 ← 이 장표가 "무엇"을 다루는가
리드 메시지  1~2문장 결론                       ← "그래서 무엇을 말하려는가"
본문        컬럼 2~3개 (소제목 + 카드/도식/표/수치)
```

### 고정 장표
| 위치 | 장표 | 필수 | 구성 |
| --- | --- | --- | --- |
| 1 | 표지 | 필수 | 상단 행사·문서명 / 제목 / 부제 / 회사명 / 발표자 또는 날짜 / 로고 |
| 2 | 목차 | 권장 | 4~7개 섹션, 번호 + 제목 |
| 섹션 시작 | 간지 | 선택 | dense 모드는 생략(헤더 번호로 대체), airy 모드는 다크 배경 디바이더 |
| 끝-1 | 마무리 | 필수 | 핵심 한 문장 / 회사명 / 연락처 / 로고 |
| 끝 | Appendix | 선택 | 질의 대비 상세 자료, 번호 없이 "Appendix – 제목" |

### 밀도 모드 기본값
| 유형 | 모드 | 이유 |
| --- | --- | --- |
| A 기술 발표, B 프로젝트 보고, C 기술 제안 | dense | 심사·평가자가 읽는다. 근거를 한 장에 |
| D IR, E B2B 소개, G 내부 보고 | airy | 듣는 자료. 메시지 하나만 크게 |
| F 고객 제안 | dense/airy 선택 | 제출용이면 dense, 미팅용이면 airy |

### 입력 수집 (공통)
- 문서 유형, 밀도 모드
- 메인 컬러(필수), 보조 컬러(선택), 로고 파일
- 회사명, 발표자/작성자, 날짜
- 원문 텍스트 또는 기존 PPTX
- 유형별 추가 질문은 각 섹션 "필수 입력" 참조

### 레이아웃 매핑 (표준 덱 템플릿 24종)

덱 템플릿의 24종 슬라이드를 이 스킬의 블록으로 옮긴 표다. 표지·목차·간지·마무리 4종은 `outline.json` 의 `meta` 만으로 자동 생성되고, 나머지 20종은 본문 장표의 `blocks` 로 만든다.

| # | 템플릿 레이아웃 | 이런 내용일 때 | 이 스킬에서 쓰는 블록 |
| --- | --- | --- | --- |
| 01 | Cover — Dark Brand | 표지 | 자동(`meta.title/subtitle/orgs/date`). 다크 표지 한 종만 쓴다 |
| 02 | Cover — Clean Light | 밝은 표지 | 쓰지 않는다(01 로 통일) |
| 03 | Agenda | 목차 | 자동(`meta.agenda`). 번호 + 섹션명만 |
| 04 | Section Divider | 단원 시작 간지 | 자동(`meta.dividers`, 목차 3개 이상이면 들어감) |
| 05 | Title + Bullet Points | 항목 3~5개 나열 | `bullets`. 4개 넘으면 `columns`/`cards` 로 |
| 06 | Title + Image Right | 텍스트 설명 + 화면·사진 | `image` (`side:"right"`, `text:{heading, items}`) |
| 07 | Title + Image Left | 이미지가 주인공, 설명은 보조 | `image` (`side:"left"`) |
| 08 | Two Columns — Equal | 두 항목을 같은 비중으로 | `columns` 2개. 전·후 대비면 `compare` |
| 09 | Three Column Cards | 환경·현황을 세 갈래로 | `cards` 3개 |
| 10 | Stats / Metrics | 성과·수치 강조 | `stats` 2~4개. 추이가 있으면 `chart`, 근거는 `table` |
| 11 | Full Bleed Image | 구성도·시연 화면 전면 | `image` (`side:"full"`) |
| 12 | Table — Comparison | 비교, 평가지표 대응, 예산 | `table` (`emphasize` 로 강조 열) |
| 13 | Quote / Testimonial | 고객 발언, 인용 | `callout` (`text`, `label:"고객 의견"` 등) |
| 14 | Timeline | 일정·연혁, 시점이 핵심 | `timeline`. 기간·동시 진행이 핵심이면 `table` 간트형 |
| 15 | Problem → Solution | 문제와 해결을 맞대어 | `compare` (`tag` AS-IS/TO-BE 또는 문제/해결) |
| 16 | Process Steps | 절차·파이프라인, 순서가 핵심 | `process` 3~5단계. 분기·반복이 있으면 `image` 흐름도 |
| 17 | 2×2 Image Grid | 시연·사례 사진 4장 | `columns` 2개(`image` 포함) 블록을 위아래 2개 |
| 18 | Team Members | 팀·조직 | `cards` 4개(`cols:4`, 제목=이름, 설명=역할). 사진은 넣지 않는다 |
| 19 | Closing / Thank You | 마무리 | 자동(`closing.message/sub`, `meta.contact`) |
| 20 | Company Overview | 회사 소개 + 지표 | `columns` 2개(좌 소개·특징, 우 `stat`) 또는 `columns` + 아래 `stats` |
| 21 | Solution Feature (A-type) | 기술 모듈 하나를 깊게 | `image` (`side:"right"`) + 아래 `callout` |
| 22 | Technical Proposal (Split) | 도전과제 ↔ 솔루션 비교 | `compare`, 표가 필요하면 `columns`(좌 items) + `table` |
| 23 | R&D Project Background | 프로젝트 배경 + 목표 4개 + 기술 태그 | `cards` 4개(`cols:2`) + `callout`(기술 태그) |
| 24 | Client / Partner Logos | 고객·파트너 로고 | `columns` 3개(`image`) 블록 2개. 로고 파일이 없으면 자리표시자 |

블록 필드는 `outline-schema.md` 의 "블록 타입" 표를 따른다.

## A. 기술 발표 — 과제 또는 공모전

심사위원 또는 평가팀이 읽는 기술 발표자료. 시제품·PoC·기술개발 과제를 심사받을 때 쓴다.

| # | 섹션 | 장표 | 리드 메시지가 답해야 할 질문 | 본문 패턴 |
| --- | --- | --- | --- | --- |
| 1 | 배경 및 문제점 | 1-1 현장 환경 | 현장은 어떤 조건인가 | 3컬럼: 환경 특성 / 기존 체계 / 데이터 특성 |
| | | 1-2 현 체계와 문제점 | 지금 무엇이 안 되는가 | 현 체계 흐름도 + 문제점 카드 3개 |
| 2 | 요구사항 및 제약 | 2-1 요구사항 | 무엇을 요구받았나 | 요구사항 표 + 대응 기술 매핑 |
| | | 2-2 데이터·환경 특성 | 데이터의 한계와 기회는 | 센서/데이터 유형별 카드 |
| 3 | 해결방안 | 3-1 추진 방향·목표 | 어떻게 풀 것인가 | 문제→해결 대응 + 목표 지표 |
| | | 3-2 시스템 구성도 | 전체 구조는 | 전폭 구성도 + 구성요소 설명 |
| 4 | 시제품 시연 | 4-1 시연 설명 | 무엇을 보여줄 것인가 | 시나리오 단계 + 화면 캡처 |
| | | 4-2 시연 영상 | | 영상 링크/썸네일 전면 |
| 5 | 핵심 기술 내용 | 5-1~5-3 모듈별 1장 | 이 모듈이 왜 차별적인가 | 입력→처리→출력 도식 + 판정 기준표 |
| 6 | 데이터 확보 방안 | 6-1 확보·처리·산출 | 데이터는 어디서 어떻게 | 확보 경로 카드 → 파이프라인 → 산출 데이터셋 |
| 7 | 활용방안 및 효과 | 7-1 활용·효과 | 도입하면 무엇이 달라지나 | 좌: 활용 절차·방안 / 우: 효과 수치 강조 |
| | 마무리 | 감사합니다 | | |
| | Appendix | 판단 예시, 구성도 상세 등 | | |

**필수 입력**: 과제·행사명, 요구사항 원문, 기술 모듈 목록, 시연 자료(영상·캡처), 효과 수치와 근거.
**변형**: 실증형이면 4장을 "실증 계획·환경"으로, 사업화형이면 7장을 "사업화 전략·매출 계획"으로 교체.

## B. 프로젝트 진행보고 — 연차·단계·최종

정부 지원 또는 내부 R&D 프로젝트의 진행 상황을 보고하는 자료. 정기 평가나 전달 보고 시 쓴다.

| 챕터 | 섹션 | 장표 | 본문 패턴 |
| --- | --- | --- | --- |
| i | 프로젝트 개요 | i-1 소개 / i-2 목표 요약 | 프로젝트 카드 + 목표 2×2 그리드 |
| ii | 추진 실적 | ii-1 진척도 / ii-2 마일스톤 / ii-3 예산 집행 | 진척률 바, 타임라인, 예산 표(집행률 강조 열) |
| iii | 개발 내용 | iii-1 추진 프로세스·기관 역할 / iii-2 핵심 지표 선정 / iii-3 핵심 기술 / iii-4 데이터셋 / iii-5 시스템 구성 / iii-6 정량 목표 달성 / iii-7 시험·검증 / iii-8~ 제품 시연 | 기술별 설명, 달성 현황 표(달성 열 강조), 증명서 contain 이미지 |
| iv | 사업화·확산 | iv-1 현황 / iv-2 인증·지정 추진 / iv-3 시제품 구성 / iv-4 목표 달성 / iv-5 특허 / iv-6 홍보·네트워크 | 로드맵, 표, 로고 그리드, 사진 그리드 |
| v | 차년도 계획 | v-1 개발·사업화 계획 / v-2 실행 로드맵 / v-3 확장 계획 | 타임라인, 3컬럼 |
| | 마무리 | 감사합니다 | |
| | Appendix | 인프라, 인력·조직, 시험 세부 | |

**필수 입력**: 프로젝트명·기간·기관, 연차 목표 vs 실적(정량), 예산 집행, 검증·인증·특허 증빙 파일.
**규칙**: 표 작성 전 강조 열 질문. 헤더 번호·페이지 번호·순서 3중 정합성 최종 점검.

## C. 기술 제안서 — 신규 과제

평가표를 목차로 삼는 제안서. 심사위원이 평가 항목 순서로 점수를 매기므로, 섹션 = 평가 항목.

| # | 섹션 | 장표 | 리드 메시지 질문 |
| --- | --- | --- | --- |
| 1 | 과제 개요 | 1-1 요약(목표·기간·예산·산출물) | 이 과제는 한 문장으로 무엇인가 |
| 2 | 필요성 | 2-1 배경(정책·시장·현장) / 2-2 문제 정의 / 2-3 기술 동향·한계 | 왜 지금, 왜 지원받아야 하나 |
| 3 | 목표 | 3-1 최종 목표·정량 지표 / 3-2 단계별 목표 | 무엇을 어떤 수준까지 |
| 4 | 개발 내용 | 4-1 시스템 구성 / 4-2~ 핵심 기술별 1장 / 4-N 데이터 확보 | 어떻게 달성하나 |
| 5 | 추진 체계·일정 | 5-1 기관별 역할 / 5-2 일정(간트) / 5-3 예산 | 누가, 언제, 얼마로 |
| 6 | 기대효과·활용 | 6-1 기술적·경제적·사회적 효과 / 6-2 사업화·활용 계획 | 끝나면 무엇이 남나 |
| 7 | 수행 역량 | 7-1 유사 과제 실적 / 7-2 보유 기술·인프라 / 7-3 인력 | 우리가 할 수 있다는 근거 |
| | 마무리 / Appendix | | |

**유형별 강조 이동**
| 과제 유형 | 비중을 늘릴 섹션 | 추가 장표 |
| --- | --- | --- |
| 기술개발 | 4 개발 내용 | 기술 차별성 비교표, 준비도 단계 |
| 실증 | 5 추진 체계 | 실증 현장·수요기관 확약, 검증 방법 |
| 사업화 | 6 기대효과·활용 | 매출 계획, 고객사·LOI, 인증 로드맵 |

**필수 입력**: 평가표 원문, 과제 유형, 정량 목표 후보, 참여기관, 예산 총액.
**금지**: 시장 규모·매출 수치를 제공받지 않고 채우지 않는다. 빈 자리는 `[입력 필요]` 플레이스홀더로 남긴다.

## D. 회사소개서 — 투자용 (IR)

| # | 섹션 | 장표 | 리드 메시지 질문 |
| --- | --- | --- | --- |
| 1 | 시장의 문제 | 1-1 문제(현장 사진·수치) | 누가 무엇 때문에 고통받나 |
| 2 | 솔루션 | 2-1 한 문장 솔루션 / 2-2 제품 화면·구성 | 우리는 무엇을 어떻게 바꾸나 |
| 3 | 시장 규모 | 3-1 TAM/SAM/SOM(출처 명기) / 3-2 시장 진입 시점 | 얼마나 큰 시장인가 |
| 4 | 기술·경쟁력 | 4-1 핵심 기술 / 4-2 경쟁사 비교 / 4-3 특허·인증 | 왜 우리만 할 수 있나 |
| 5 | 비즈니스 모델 | 5-1 수익 구조 / 5-2 가격 | 어떻게 돈을 버나 |
| 6 | 트랙션 | 6-1 매출·고객 / 6-2 성장 지표 / 6-3 파트너 로고 | 실제로 팔리고 있나 |
| 7 | 팀·배경 | 7-1 팀 / 7-2 연혁·조직 | 누가 하나 |
| 8 | 투자 계획 | 8-1 요청액·용도 / 8-2 마일스톤·Exit | 돈을 받아 무엇을 하나 |
| | 마무리 | 연락처 | |

**필수 입력**: 매출·고객 수치, 시장 규모 출처, 팀 프로필, 투자 요청액과 계획. 수치 없으면 해당 장표는 플레이스홀더.
**모드**: airy. 장표당 메시지 1개, 수치는 큼.

## F. 고객사 제안서 — 솔루션 제안

고객명·현장이 바뀌는 장표와 고정 장표를 분리한다. 스킬은 `variable` 표시 장표만 재생성한다.

| # | 섹션 | 장표 | 고정/변동 | 리드 메시지 질문 |
| --- | --- | --- | --- | --- |
| 표지 | | 고객사명 + 제안명 + 날짜 | 변동 | |

## 부록. 기존 PPTX 개선 모드

업로드된 PPTX의 장표 제목을 읽어 위 A~G 중 가장 가까운 템플릿을 추정한다. 다음 순서로 진행:

1. 추정 유형과 매핑 결과(장표 → 템플릿 섹션)를 보여주고 확인받는다.
2. 누락 섹션은 "추가 권장"으로, 템플릿 밖 장표는 "유지/Appendix 이동/삭제" 중 선택받는다.
3. 원문 텍스트는 의미를 유지하고 리드 메시지만 새로 쓴다. 수치는 절대 바꾸지 않는다.
