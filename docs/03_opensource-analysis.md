## 1. 영문 세 곳

### 1-1. ppt-master (MIT, 55.6k)

문서나 주제를 넣으면 네이티브 PPTX를 만드는 Claude Code 스킬이다. SVG로 한 장씩 그린 다음 PowerPoint 도형으로 옮긴다. 우리가 HTML로 그리고 PPTX로 옮기는 것과 경로가 같다.

핵심은 문서를 **역할별로 쪼개 놓고 필요한 것만 읽는 구조**다. 스킬 문서가 229개에 54만 토큰인데, 실행할 때는 `SKILL.md`(2.6k) → `routing.md` → 고른 경로 하나만 읽는다. 경로는 다섯 가지다. 새로 만들기, 빠르게 만들기, 이미지에서 만들기, 기존 PPTX 다듬기, 템플릿 만들기.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | 라우팅으로 토큰을 끊어 쓴다. 템플릿을 브랜드·스타일·레이아웃·덱 네 겹으로 나눴다. 말투 모드 5종이 목차 뼈대를 정한다. 지어낸 수치에 `Data class: scenario` 딱지를 붙인다 |
| 안 좋은 점 | 문서가 지나치게 많고 규칙 문장이 난해하다. 실행 전에 무결성 검사기가 돌아서, 후원사 파일을 지우면 스킬이 멈춘다. 확인 단계가 두 번 막혀 있어 빠른 초안에는 무겁다 |
| 우리와 겹치는 것 | SVG/HTML 중간 산출물 → 네이티브 PPTX 변환, 기존 PPTX 개선 모드 |

### 1-2. Presenton (Apache-2.0, 10.6k)

Docker로 띄우는 완성품 서비스다. 웹 화면, API, MCP 서버, 데스크톱 앱까지 있다. 모델은 OpenAI·Claude·Gemini·Ollama 중에 고른다.

우리가 가장 크게 배울 곳은 **LLM 호출 횟수를 줄인 설계**다. 슬라이드가 N장일 때 호출이 N+2번으로 끝난다.

1. 목차 1회. 슬라이드마다 `## 제목` + 본문을 마크다운으로 받는다. 이때 레이아웃은 정하지 않는다
2. 레이아웃 배정 1회. 레이아웃 12종 설명을 한 번 주고 `[0, 1, 2, 3, 4]`처럼 장별 번호만 받는다
3. 장별 내용 N회. 그 장에 배정된 레이아웃의 JSON 스키마만 주고 값을 채우게 한다

장마다 24종 전체를 다시 설명하지 않는 게 요점이다. 분량 제한도 코드에 박아 뒀다. 한 장 100단어, 최대 50장, 말투에 따라 20/40/60단어.

Template V2는 기존 PPTX를 업로드하면 레이아웃 묶음으로 바꿔 준다. 시각 모델이 장마다 네 번 훑는다. 차트·표 찾기 → 어디가 고칠 수 있는 자리인지 표시 → 반복되는 영역 찾기 → **글자가 몇 자까지 들어가는지 계산**. 마지막 항목이 기획서 3.2의 "내용이 늘거나 줄어도 안 깨진다"를 푸는 방법이다.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | 호출 N+2번. 레이아웃 배정을 한 번에 끝냄. 기존 PPTX를 템플릿으로 흡수. 글자 수용량을 기계가 계산 |
| 안 좋은 점 | 디자인이 서양 슬라이드 톤이라 한글 조판 처리가 없다. 레이아웃이 템플릿당 12종으로 우리 24종보다 적다. 한 덱에 10~40장 만들면 컨테이너 CPU가 337%까지 치솟는다 |

### 1-3. PPTAgent (MIT, 5.0k)

논문에서 출발한 연구 코드다(ACL 2026). 다른 두 곳과 접근이 다르다. 새로 그리지 않고 **기존 발표자료를 뜯어서 고쳐 쓴다.**

1단계에서 참고 덱을 분석한다. 장을 역할로 나누는데, 표지·목차·간지·마무리는 LLM이 찾아내고 본문 장은 이미지 유사도로 묶는다(기준값 0.65). 장마다 요소를 분류·설명·값 세 항목으로 스키마를 뽑는다.

2단계에서 원고를 참고 장에 매칭하고, 편집 명령으로 고친다. 명령은 다섯 개뿐이다. `del_span`, `del_image`, `replace_span`, `replace_image`, `clone_paragraph`. 슬라이드를 XML이 아니라 HTML로 보여 줘야 LLM이 잘 읽는다는 것도 논문이 실험으로 보였다.

PPTEval이라는 채점기가 따로 있다. 내용·디자인·흐름을 1~5점으로 매기고, 사람 평가와 상관계수 0.71이 나왔다. 평균 3.67점, 성공률 95%.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | 장 역할 분류와 스키마 추출 방식. 편집 명령 5개로 부분 수정을 표현. 결과물 채점기(PPTEval) |
| 안 좋은 점 | 장마다 LLM을 여러 번 부르고 재시도까지 해서 토큰을 가장 많이 쓴다. 참고 덱 품질에 결과가 끌려간다. 설치에 LibreOffice·uv·npm이 다 필요하다 |

## 2. 한글 세 곳

### 2-1. mckinsey-pptx (MIT, 586)

AX Labs가 만든 Claude Code 플러그인이다. 슬라이드 템플릿 40종을 파이썬 패키지로 넣어 두고, 서브에이전트가 내용을 보고 템플릿을 고른다. 한글 요청을 받으면 한글로 만든다.

카탈로그가 잘 쓰였다. 템플릿마다 다섯 항목이 고정이다.

- **Use when** 이 템플릿이 맞는 상황
- **Don't use when** 헷갈리는 이웃 템플릿과 왜 다른지
- **Required inputs** 반드시 넣어야 하는 값
- **Optional inputs** 더 넣으면 좋은 값
- **Example** 그대로 돌아가는 호출 예시

뒤에 "비슷한 템플릿 중에 고르기" 절이 또 있다. 숫자가 하나면 `stat_hero`, 타일로 여러 개면 `kpi_dashboard`, 사업부별 목표·실적·신호등이면 `assessment_table` 같은 식이다.

에이전트에게 요구하는 것도 분명하다. 장마다 고른 템플릿과 **왜 옆 템플릿이 아닌지 한 줄로 쓰게** 한다. "9개 과제를 영향도×소요시간으로 놓았다. 축이 시장점유율이 아니라서 `growth_share`가 아니다" 같은 문장이다.

한글 관련해서 실측값이 들어 있다. 제목은 한글 50자·영문 70자 이하, 좁은 칸은 한글 6어절·영문 10단어 이하, 한글은 같은 크기에서 라틴 문자보다 1.3배 넓으니 영문 대비 25% 짧게 쓰라고 못 박았다.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | 40종 카탈로그 형식. 선택 이유를 말로 남기게 함. 한글 글자폭 실측값. 덱 하나를 파이썬 스크립트 한 개로 만들어 호출이 적다 |
| 안 좋은 점 | 2026년 4월 이후 갱신이 없다. 맥킨지 톤 고정이라 형식이 정해진 제안서에는 안 맞는 장이 많다. 폰트가 Apple SD Gothic Neo라 Windows에서 깨진다. 표지·간지·목차가 40종 중 5종뿐이라 문서 뼈대가 약하다 |

### 2-2. korean-presentation-skill (MIT, 2)

우리 파이프라인과 가장 비슷하다. 마크다운 → HTML 미리보기 → 기계 검수 → 네이티브 PPTX 순서다. 검수에서 `error`가 하나라도 나오면 PPTX 변환을 막는다.

검수 규칙이 14개다. 우리 `check_overflow.mjs`는 캔버스 밖으로 나갔는지와 잘렸는지 두 가지만 본다.

| 규칙 | 수준 | 내용 |
| --- | --- | --- |
| `canvas-overflow` | error | 1280×720 밖으로 넘침 |
| `low-contrast` | error/warn | 실제 칠해진 배경 대비 WCAG AA 미달 |
| `empty-slide` | error | 글도 그림도 없음 |
| `letter-spacing` | warn | 자간이 -0.025em 기준에서 벗어남 |
| `word-break-root` / `word-break` | warn | `keep-all` 미선언 |
| `korean-orphan` | warn | 마지막 줄에 한두 글자나 조사만 남음 |
| `font-too-small` | warn | 11px 미만 |
| `unsafe-font` | warn | PowerPoint 기본 환경에 없는 폰트 |
| `text-collision` | warn | 글 상자끼리 30% 이상 겹침 |
| `vertical-imbalance` | warn | 위아래 여백 차이가 캔버스의 28% 초과 |
| `missing-notes` / `thin-notes` | warn/info | 발표자 노트 없음이나 너무 짧음 |
| `gradient-approximated` | info | CSS 그라데이션이 PPTX 단색으로 근사됨 |

자간 규칙을 두 겹으로 나눈 이유까지 적어 뒀다. CSS는 `em` 자간을 선언한 요소에서 한 번 px로 확정하고 자식에게 그 px를 물려준다. 그래서 자식의 실효 비율은 제 글자 크기에 따라 달라진다. 처음엔 이걸 기준과 바로 비교해서 오탐이 130건(경고의 78%) 나왔고, 지금은 루트에서 선언값을 한 번만 보고 개별 블록은 읽을 수 있는 한계만 본다.

왜 HTML을 거치는지도 숫자로 남겼다. marp-cli로 뽑으면 장마다 배경 PNG 한 장이라 편집 가능한 텍스트가 0개, 2장짜리가 421KB다. 직접 도형으로 쓰면 66KB에 텍스트가 수십 개다.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | 검수 규칙 14개와 차단 기준. 한글 조판 규칙(자간 -0.025em, `keep-all`, 외톨이 글자). 감사 결과를 `audit.json`으로 남김. 오탐을 줄인 과정을 기록 |
| 안 좋은 점 | 마스터 레이아웃이 8종뿐이다. 주제에 따라 색을 매번 새로 만드는 방식이라 회사 색 고정과 맞지 않는다. 별 2개짜리 신생 레포라 갑자기 멈출 수 있다 |

### 2-3. ppt-deck (MIT, 0)

"AI가 찍어낸 티가 나지 않는" 한글 PPTX를 목표로 한 Claude Code 스킬이다. 디자인보다 **문장과 리듬**을 먼저 잡는다.

린터가 잡는 패턴이 우리 기획서에 없는 것들이다.

| 코드 | 무엇을 잡나 |
| --- | --- |
| `RHYTHM` | 같은 레이아웃 3연속 |
| `DENSITY` | 한 장에 말할 수 있는 양을 넘긴 불릿 |
| `SENTENCE` | 완전한 문장. 불릿은 명사구로 끝내야 한다 |
| `UNIFORM` | 불릿 길이가 부자연스럽게 고른 것 |
| `PARALLEL` | "X의 이해 / X의 활용 / X의 전망" 같은 병렬 제목 |
| `EMOJI` | 이모지 |
| `CLICHE` | 다양한, 효율적, 혁신적, 극대화, 살펴보겠습니다 |

레이아웃을 고를 때 사람이 개입할 여지를 없앤 것도 눈에 띈다. `cards`는 **항목 수만으로** 모양이 결정된다. 2개면 pair, 3개면 ledger, 4개면 quad, 5~6개면 dense, 1개면 다른 레이아웃으로 바꾸고, 7개 이상이면 장을 쪼갠다. 모드를 직접 지정하는 옵션 자체가 없다.

한글 PPTX에서 걸리는 함정 세 가지도 코드로 풀어 놨다. python-pptx가 `<a:latin>`만 쓰는 문제를 `<a:ea>` 태그로, 편집할 때 폰트가 바뀌는 문제를 `<a:endParaRPr>` 채우기로, OTF를 거부하고 TTF만 쓰는 것으로 막는다. 외부 렌더러 없이 Pretendard TTF를 PIL로 직접 읽어 SVG 미리보기를 만든다.

| 항목 | 내용 |
| --- | --- |
| 좋은 점 | AI 티 린터 7종. 항목 수가 레이아웃을 정하는 규칙. 한글 폰트 XML 처리. 디자인 원칙 11개에 근거가 붙어 있음 |
| 안 좋은 점 | 강의 덱을 염두에 둬서 제안서·보고서 뼈대가 없다. 레이아웃 11종. 팔레트가 3색 고정이라 회사 색 체계를 그대로 못 넣는다 |

## 4. 목차를 어떻게 짜는가

여기가 우리와 가장 다른 곳이다. 우리는 문서 종류가 목차를 정한다. 저쪽은 대부분 **말하는 방식**이 목차를 정한다.

### ppt-master: 말투 모드 5종이 목차를 정한다

덱마다 모드를 하나 고르고, 그 모드가 장 순서·제목 어조·밀도를 다 정한다. 보기 방식(text/balanced/presentation)은 따로 고른다.

| 모드 | 이야기 뼈대 | 쓰는 자리 |
| --- | --- | --- |
| pyramid | 결론 먼저. SCQA로 열고 근거를 구조로 쌓음 | 의사결정, 전략, 경영진 보고 |
| narrative | 상황 → 긴장 → 해소 | 피치, 사례, 투자 유치 |
| instructional | 개념 분해 후 단계별 설명 | 교육, 설명회 |
| showcase | 큰 그림과 숫자로 밀어붙임 | 출시, 브랜드 공개 |
| briefing | 주제형 제목, 고른 비중, 주장 없음 | 현황 보고, 참고 자료, 회의 자료 |

pyramid 모드에는 제목 쓰는 법이 예시로 붙어 있다. **제목이 결론이어야 한다**는 규칙을 문장으로 보여 준다.

| 약한 제목(주제) | 강한 제목(주장) |
| --- | --- |
| 시장 개요 | 국내 시장은 연 23% 성장해 세계 평균을 앞선다 |
| 문제점 | 세 가지 구조적 모순이 확산을 막는다 |
| 우리의 해결책 | 3단계 경로. 집중, 확장, 규모화 |

장마다 `Audience move`(이 장이 듣는 사람을 어디로 옮기는가)를 쓰게 하고, **아무것도 진전시키지 못하는 장은 합치거나 지운다.** 표지·간지·마무리도 예외가 없다.

### Presenton: 뼈대 없이 규칙만 둔다

목차를 문서 종류로 나누지 않는다. 표지 넣을지, 목차 장 넣을지만 켜고 끈다. 대신 규칙이 있다.

- 장마다 목적 하나. 내용이 넘치면 장을 쪼갠다
- 같은 사실을 여러 장에서 반복하지 않는다
- 도입부터 마무리까지 하나의 이야기로 잇는다
- 표현 방식을 섞는다. 불릿, 비교, 시간순, 표, 지표
- 장 내용에 "이 슬라이드는", "다음 장에서는" 같은 말을 쓰지 않는다

마지막 규칙이 쓸 만하다. 발표자료 자체를 설명하는 문장을 금지어로 못 박았다.

### PPTAgent: 참고 덱에서 목차를 읽어 온다

목차를 만들지 않고 꺼내 온다. 참고 덱의 장을 구조 장(표지·목차·간지·마무리)과 본문 장으로 가르고, 본문 장은 생긴 모양으로 묶는다. 원고를 그 묶음에 배정하면 목차가 나온다. 목차 항목은 참고 장 지정, 들어갈 원고 내용, 출처 세 가지다.

### mckinsey-pptx: 컨설팅 이야기 순서 하나

5~10장을 기본으로 한다.

1. 표지 또는 `dark_navy_summary`로 결론 한 문장
2. `executive_summary_takeaways`로 논지 구조화
3. 분석 장 1~3개. 차트, 매트릭스
4. 시사점 장 1~2개. 영역, 추세, 우선순위
5. 로드맵이나 프로세스 1개
6. 마무리 권고 1개

"6장이면 될 걸 15장 만들지 마라"가 에이전트 지침에 금지 사항으로 들어 있다.

### ppt-deck: 강의 이야기 순서

질문 → 대립 → 정의 → 역사 → 원리 → 적용 → 듣는 사람 삶과의 연결 → 열린 질문 셋 → 질문 시간. 마지막을 요약이 아니라 질문으로 끝내는 게 특징이다. 파트가 바뀔 때마다 간지를 같은 좌표로 반복해서 진행 위치가 저절로 읽히게 한다.

### korean-presentation-skill: 레이아웃 8종이 곧 흐름

표지 → 비대칭 2단 목차 → 3단 분석 → 파이프라인 → 비교 매트릭스 → 대형 지표 → 인용 → 마무리·Q&A. 레이아웃 목록이 그대로 덱 순서를 암시한다.

### 우리와 견주면

우리는 6.3에 문서 6종의 목차를 장수까지 적어 뒀다. 형식이 정해진 제안서 7챕터 10항목, 고객사 제안서 8챕터, 연차보고서 5챕터 12항목 같은 식이다. 저쪽 어디에도 이만큼 구체적인 목차표가 없다.

그래서 이렇게 갈린다.

| | 우리 | 오픈소스 6곳 |
| --- | --- | --- |
| 강점 | 형식이 정해진 문서처럼 형식이 정해진 문서에서 바로 쓴다 | 형식이 없는 문서도 만든다 |
| 약점 | 6종 밖의 문서는 기댈 데가 없다. 장별 제목을 어떻게 쓰라는 규칙이 없다 | 평가지표 대응 같은 구조를 못 만든다 |

우리 6.3 표에 빠진 칸이 하나 있다. **장마다 무엇을 주장하는가**다. 지금은 "무엇을 쓰나"까지만 있고(예: "운용 환경의 특성"), 그 장의 결론을 어떻게 쓸지는 비어 있다. 3.1에 "제목 아래 한 줄 결론 한 문장"이 조건으로는 있지만, 6.3 표와 이어지지 않는다.

## 5. 토큰을 얼마나 쓰는가

두 가지를 따로 봐야 한다. 매번 읽어 들이는 지시문 양과, 덱 하나에 LLM을 몇 번 부르는지다.

### 5-1. 지시문 양 (추정)

한글 한 글자를 1토큰, 영문 3.8자를 1토큰으로 잡아 계산했다. 실제 토크나이저와 10% 안팎 차이가 난다.

| 시스템 | 실행마다 읽는 문서 | 추정 토큰 |
| --- | --- | --- |
| ppt-master (SKILL만) | SKILL.md | 2,619 |
| ppt-master (빠른 경로) | SKILL + routing + quick-generate | 16,164 |
| ppt-master (기본 경로) | 위 + strategist + plan-core + 모드 + 스타일 + 실행자 + 표준 | 63,935 |
| ppt-master (전체 문서고) | md 229개 | 546,496 |
| mckinsey-pptx | 에이전트 지침 + CATALOG.md | 11,632 |
| korean-presentation-skill | SKILL + 레이아웃 카탈로그 + 조판 가이드 | 16,468 |
| korean-presentation-skill + 템플릿 1종 | 위 + 템플릿 | 21,199 |
| ppt-deck | SKILL + 스펙 yaml | 19,511 |
| Presenton (목차 프롬프트) | 시스템 프롬프트만 | 약 1,200 |
| **우리 ppt-maker (SKILL만)** | SKILL.md | **3,886** |
| **우리 ppt-maker (레퍼런스 포함)** | SKILL + references 4개 | **20,888** |

우리 21k는 여섯 곳 중간쯤이다. 문제는 양이 아니라 **한 번에 다 읽는다**는 점이다. ppt-master는 54만 토큰을 갖고 있으면서 실행에는 16k만 쓴다. `design-system.md` 하나가 7,950토큰인데, 목차를 짤 때는 디자인 규칙이 필요 없다.

### 5-2. 호출 횟수 (18장 기준)

| 시스템 | 호출 구조 | 18장이면 |
| --- | --- | --- |
| mckinsey-pptx | 카탈로그 1 + 구성 1 + 스크립트 1 + 렌더 확인 1~2 | 4~5회 |
| Presenton | 목차 1 + 레이아웃 배정 1 + 장별 내용 N | 20회 |
| ppt-deck | 아웃라인 1 + 린트·빌드 반복 | 3~6회 |
| korean-presentation-skill | 마크다운 1 + 감사 반복 | 3~6회 |
| ppt-master 기본 | 확인 2 + 설계서 2 + 장별 SVG N + 품질 검사 | 25회 이상 |
| PPTAgent | 장별 편집 + 재시도 최대 2 + 시각 검토 | 40회 이상 |
| **우리** | 장별 생성 (입력 20.7k·출력 10.5k) | **입력 373k·출력 189k** |

기획서 1.2에 적힌 우리 수치가 장당 입력 20.7k다. Presenton이 장별 호출에 싣는 건 그 장에 배정된 레이아웃 스키마 하나뿐이라 훨씬 가볍다.

여기서 나오는 선택은 둘이다. **덱 하나를 산출물 한 개로 쓰게 하거나**(mckinsey-pptx가 파이썬 스크립트 한 개, ppt-deck이 yaml 한 개), **장별 호출을 하되 그 장에 필요한 것만 싣거나**(Presenton). 지금 우리는 장별로 부르면서 전체 맥락을 매번 싣고 있을 가능성이 높다.

**4. 지어낸 수치에 딱지를 붙인다.** CLAUDE.md와 PRD 1.5에 "임의 생성 금지"가 있지만, 실제로는 예시 수치가 필요한 장이 있다. ppt-master처럼 `Data class: scenario`를 붙여서 결과 보고에 "이 숫자는 사용자가 준 것, 저 숫자는 예시"라고 구분해 알린다.

**7. 레퍼런스를 단계별로 쪼개 읽는다.** 지금 4개 파일 21k를 한 번에 읽는다. 이렇게 나눈다.

| 2 아웃라인 | outline-schema + outline-templates | 약 8,900 |

**8. 레이아웃 배정을 한 번에 끝낸다.** Presenton 방식이다. 목차가 나오면 레이아웃 24종 요약을 한 번만 주고 `[1, 9, 16, 12, 11, ...]`로 받는다. 그다음 장별 생성에는 그 장 레이아웃의 블록 스키마만 싣는다. 장당 입력 20.7k가 크게 줄어든다.

**9. 항목 수가 레이아웃을 정하게 한다.** ppt-deck의 `cards` 규칙이다. 우리 6.5에서 09 카드3, 23 목표4, 08 2단은 사실상 항목 수로 갈린다. LLM에게 고르게 하지 말고 숫자로 자동 결정하면 판단 한 번이 줄고 결과가 일정해진다.

### 참고만

**10. 기존 PPTX 개선의 글자 수용량 계산.** Presenton Template V2가 시각 모델로 "이 자리에 몇 자까지 들어가는가"를 재 둔다. 우리 PPTX 개선 모드에 같은 걸 붙이면 좋지만, 시각 모델 호출이 장마다 네 번이라 비싸다. 나중에 본다.

**11. 브랜드·스타일·레이아웃 분리.** ppt-master가 템플릿을 네 겹으로 나눴다. 우리는 회사 색이 고정이라 지금은 이득이 적다. 타사 소개서를 만들 때 필요해진다.

**12. PPTEval 채점.** PPTAgent의 내용·디자인·흐름 3항목 채점이다. 1.4 성공 지표에 "수정 횟수·시간"만 있는데, 결과물 품질을 재는 눈금이 따로 있으면 템플릿을 고칠 근거가 생긴다.

## 8. 가져오지 않을 것

| 무엇 | 왜 |
| --- | --- |
| 주제별 동적 색 생성 (korean-presentation-skill) | 회사 색이 정해져 있다. 3.1 "우리 회사 자료로 보인다"와 정면으로 어긋난다 |
| 무결성 검사기 (ppt-master) | 후원사 표시를 강제하는 장치다. 사내 도구에 필요 없다 |
| 확인 단계 2회 차단 (ppt-master) | 5장 UX 플로우가 이미 8단계다. 더 막으면 느려진다 |
| 맥킨지 톤 고정 (mckinsey-pptx) | 형식이 정해진 제안서와 연차보고서는 다른 형식을 요구한다 |
| 참고 덱 기반 생성 (PPTAgent) | 참고 덱 품질에 결과가 끌려간다. 우리는 템플릿을 직접 만든다 |
| AGPL 코드 (PPTist) | 웹으로 서비스하면 소스 공개 의무가 붙는다 |
| 라이선스 없는 코드 (consulting-pptx) | 쓸 권리가 없다. 구조만 눈으로 본다 |
